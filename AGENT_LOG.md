# Agent-drafted components and what we checked

Later additions from Codex are documented separately in [docs/CODEX_CHANGES.md](docs/CODEX_CHANGES.md). The historical component table below describes Claude drafts and earlier fixes; it should not be attributed to this Codex implementation pass.

The project guide requires each member to walk through one component that a coding agent drafted,
covering what it does, one thing that was wrong or unclear in the agent's version, and how the team
checked it. A different component is needed for the prototype and the final video. Every item below
was drafted by Claude Code (Claude Opus 5.5). The issues are the real ones found during development.

Suggested split: each member takes one row for the prototype and a different one for the final.

| # | Component (file) | What it does | What was wrong or unclear in the agent's draft | How it was checked or fixed |
|---|---|---|---|---|
| 1 | Input loader (`src/vrptw/instance.py`) | Reads the 4 CSVs, applies the four input checks, and builds the integer-indexed travel matrix | The first draft read CSVs with automatic type inference, so a bad value such as `capacity = sixty` crashed inside Polars without naming the column. It also left an unused duplicate reader function | Changed to read every column as text, then cast with `strict=False` and report which file and column failed. Tests: `test_missing_required_column_is_rejected` and five more malformed copies in `test_other_malformed_inputs_are_rejected` |
| 2 | Rule to beat (`src/vrptw/rule.py`) | Nearest feasible neighbor, one vehicle at a time | Unclear point: "nearest" could mean nearest by arrival time (including waiting) or by travel time. The brief says travel time from the current location, ties by customer id | `test_rule_reproduces_worked_example` matches every visit, arrival, service start, return time, and the 352.417 total from `worked-example/` |
| 3 | O(1) insertion test (`Route.insertion_cost` in `lns.py`) | Decides in constant time whether a customer can be inserted between two stops without breaking any later window | The `latest` array is indexed by route position (depot = 0), not by sequence index. An off-by-one here silently allows late deliveries | Every plan is re-verified by the independent checker. `cli.py` also refuses to export a plan that fails a full forward-pass check |
| 4 | Local search moves (`_two_opt`, `_or_opt`, `_relocate`, `_swap`, `_two_opt_star`) | VND improvement: five moves, the first improving move is applied | (a) The first draft recomputed whole-route travel for every candidate. Profiling showed this was most of the runtime, so moves now compute the change from the 2–4 altered edges (3.9× faster, identical results). (b) The 2-opt shortcut formula is only correct for **symmetric** travel times; on asymmetric data it could accept a worse move and loop forever. (c) The data break the triangle inequality slightly (108 triples in development_large), so removing a customer can in principle make a route infeasible | (a) Profiled with cProfile; results compared before and after. (b) 2-opt now confirms the true travel change before accepting. (c) `_relocate` re-checks the shortened route |
| 5 | Ruin-and-recreate loop (`solve_lns`, `_ruin_and_recreate`) | Removes q customers, reinserts them with regret insertion, runs local search, applies simulated-annealing acceptance | (a) The worst-removal operator in the first draft had a syntax slip (`append(x, c)` instead of `append((x, c))`) that crashed at runtime. (b) Testing on 60-customer proxy instances showed that more iterations (2000 → 5000) rarely helped, while changing the seed moved results by 1–4%. (c) Regret insertion evaluated every one of the identical empty vehicles. (d) After each ruin-and-recreate, local search re-scanned every pair of routes, although most were unchanged and already locally optimal. A full run on development_large took several minutes, risking the time cap | (a) Caught by running the code. (b) Tried restarts (several seeded runs, keep the best). After the speedups below, the real cause was found: the agent's starting temperature (0.02 × travel / n ≈ 0.5 min) was too cold, so the search almost never accepted a worse plan and every seed got stuck on 1047.6 for medium. Re-tuned with the Ropke & Pisinger rule (a plan 0.5% worse is accepted with probability 0.5). 1x8000, 4x2000, and 8x1000 then tied within 0.1%, so the default is one run of 8000. (c) Only one empty vehicle per (capacity, shift) type is evaluated. (d) Local search now only searches pairs that include a changed ("dirty") route, which keeps the same local-optimum guarantee. 1000 iterations on development_medium went from ~10 s to 1.3 s. `test_lns_is_deterministic` and `test_heterogeneous_fleet_is_respected` cover these |
| 6 | Independent checker (`src/vrptw/checker.py`) | Recomputes every time and measure from the CSVs and decision.json | Unclear point: should it trust the reported arrivals? No. The instructor's checker reads only the visits, so ours recomputes the times and only *warns* if the reported times differ | `test_checker_flags_a_broken_decision` feeds it a reversed route and a dropped customer and confirms both are reported. The checker imports nothing from the solver |
| 7 | Stress test (`src/vrptw/stress.py`) | Generates 30 saved travel-time scenarios and executes both fixed plans | A lognormal with "mean 1" needs μ = −σ²/2. Using μ = 0 would bias every scenario upward by about 2%. The agent's first symmetric version took the geometric mean of the i→j and j→i draws, which quietly lowered the noise to mean ≈ 0.9975 and CV ≈ 0.07 instead of the documented 1 and 0.1 | Now mirrors the upper triangle; sample mean and CV checked against 1 and 0.1. Scenarios are written to Parquet before either plan is executed |
| 8 | Comparison script and Windows output (`scripts/compare.py`) | Regenerates every table and plot | Printing Polars tables on this Windows machine crashed with `UnicodeEncodeError: 'charmap'` (box-drawing characters) | Pixi sets `PYTHONIOENCODING=utf-8`, and the script uses ASCII table formatting |
| 9 | Gurobi benchmark (`scripts/gurobi_benchmark.py`) | Exact MIP that checks how close the LNS is to optimal | Unclear points: (a) a Gurobi solve cannot be part of the graded tool (personal license), so it lives in a separate Pixi environment; (b) the first summary table claimed one time limit for every row, although rows had been run with different limits | (a) `pixi run solve/test/compare` never import gurobipy. (b) The table now records each row's `time_limit_s`. Gurobi's routes were also verified by our independent checker |
| 10 | Independent review fixes (`lns.py`, `cli.py`, `instance.py`, `gurobi_benchmark.py`, `compare.py`) | An independent AI review (Sol 6.1, `review/REVIEW_PLAN.md`) reproduced eight defects the 16 original tests missed | (a) The LNS could keep a plan that broke a window when a removal made a route late on non-metric travel times. (b) An infeasible run left an earlier decision.json in place. (c) The time cap was only checked between iterations. (d) A huge integer crashed instead of giving an input error, and Float64 parsing silently rounded integers above 2^53. (e) compare did not stop on a failed check. (f) The Gurobi arc pruning assumed direct legs are fastest. (g) 2-opt missed improvements on one-way travel times. (h) I reported the large-instance gap as "at most 26.7% above optimal"; that number is the most of our cost an optimal plan could save, and the above-optimal bound is 36.5% | Each was reproduced first, then fixed, with a regression test in `tests/test_review_fixes.py` (20 new tests, 36 total). Our own test of the integer fix caught a second rounding case the review had not listed. On the supplied data, (a) and (f) were shown never to trigger (0 of 60,000 removals; 0 wrongly pruned arcs), so every earlier result stood, and the regenerated travel times are identical |
| 11 | Management scenarios (`scripts/scenarios.py`, `scripts/scenario_explorer.html`) | Builds cushion and spare-capacity plans by running the unchanged LNS on a planning copy with tighter windows or capacity, scores them on the real instance and the saved stress scenarios, and writes the interactive page | (a) The draft included a "9-hour day" plan (every truck back by minute 540); the LNS found no plan, and the data show none exists, because C039 opens at 500 and its truck cannot return before 560.4. ## Other observations worth mentioning
- One timing run on a 60-customer proxy took 170 s instead of ~5 s. Rerunning gave the identical answer in 4 s, so the cause was the machine (sleep or contention), not the algorithm. This is why the iteration count is the stopping rule and the 480 s time cap is only a safety net.
- Tools used: Claude Code (Claude Opus 5.5) for research, drafting code and tests, profiling, and debugging. The team reviewed every component and can explain it.

## Codex review and additions — October 29, 2026

Codex independently reviewed the existing implementation, ran separate block-removal and route-pool experiments, and added fresh paired traffic evaluations. The experiments improved nominal large-instance travel but increased late events under the tested traffic model, so the existing LNS remains the recommended prototype solver.

Inside the deliverable repository, Codex added `scripts/prototype_demo.py`, the `prototype-demo` Pixi task, beginner presentation/change guides, and README links. The original solver modules, supplied inputs, defaults, dependencies, lockfile, and original results were preserved. The experiment code is kept outside this repository. The presentation (since redesigned) is in `presentation/`.

All 37 original project tests and both demo modes passed. Codex ran them with the project's Python directly because Pixi crashed in its sandbox; they were later confirmed through `pixi run` in a normal terminal, and a clean `pixi install` from a fresh clone also worked. Team members still need to personally rehearse and confirm their review; Codex has not performed that team activity on their behalf.
