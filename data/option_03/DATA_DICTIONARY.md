# Project data dictionary

The seven packages contain synthetic operating data generated by the instructor. Option 4 measures
time in working days. All other options measure time in minutes. Distances are in meters for option
5. Weights, priorities, and visit values are priority scores, not monetary estimates.

Every CSV file has a header row. Identifiers are strings and must be matched by value, never by row
position. An empty cell in an optional column means the value is absent (null). Each instance
directory also contains `schema.json`, which lists every file, column, type (`string`, `integer`, or
`number`), and whether the column may be empty, and `instance.json`, which records the option,
profile, seed, time unit, and the condition the instance is designed to test. The `row_count` in
`schema.json` describes the supplied file only, so a loader must accept a different number of rows.
The schema version is 4, recorded as `schema_version` in each `instance.json`. Version 4 (October
2026) removed the option 2 `disruptions.csv` file, the option 7 `day_config.csv` file, the empty
locked columns in options 1 and 4, and the unused `distance` and `fixed_cost` columns in options 3
and 7, and it changed no other value.

The following conventions apply to every option:

- A start time is inclusive and a completion time is exclusive, so a resource can begin its next
  task at exactly the time the previous task completes.
- Travel-time tables contain one row for every ordered pair of locations, including a zero row from
  each location to itself.
- Due dates and due times are soft targets that measure lateness. Time windows, shifts, capacities,
  and availability intervals are hard constraints that a feasible decision must satisfy.
- Coordinates support maps and plots only. The travel-time table determines travel.
- Time windows include both endpoints, so service may start exactly at the window end.

A tool must reject input that fails any of the following four checks, with a message naming the file
and column:

- every required file and column is present;
- every value has its declared type, and every column that `schema.json` marks as not nullable is
  filled;
- every identifier referenced from another file exists (e.g., every operation's `job_id` appears in
  `jobs.csv`); and
- processing times and activity durations are positive.

Every graded file, including the held-out case, otherwise keeps the structure of the supplied
files: identifiers that define an entity are unique, travel tables are complete, and intervals start
before they end. A malformed file used in grading breaks one of the four checks above.

## Option 3: Planning delivery routes

- `depots.csv` has the single `DEPOT` node and its display coordinates.
- `customers.csv` has `customer_id`, display coordinates `x` and `y`, `demand` (units),
  `service_time`, `window_start`, and `window_end`. Every customer must be served, and both window
  columns are always filled.
- `vehicles.csv` has `vehicle_id`, `capacity` (units), `shift_start`, and `shift_end`. Unused
  vehicles are allowed.
- `travel_times.csv` has `from_id`, `to_id`, and `travel_time` (minutes) for every ordered pair of
  depot and customer identifiers.
- A vehicle leaves `DEPOT` at its shift start, makes at most one route, and must return by its shift
  end. A vehicle that arrives before a window opens waits. Service must start no later than
  `window_end`, although it may finish afterward.
- The edge case has a customer whose demand exceeds every vehicle's capacity, so no feasible
  decision exists.
